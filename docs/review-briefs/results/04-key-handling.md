## Findings

### F1 — Private-key loading accepts files with unsafe permissions

**Severity: Medium in a multi-user/shared-host deployment; Low on a single-user host with correctly managed state directories**  
**Location:** `src/knok/identity.py:94-111`; caller: `src/knok/cli.py:67-75`. *Verified at 828c9791:* `Identity.save` spans `src/knok/identity.py:86-96` and `Identity.load` spans `src/knok/identity.py:106-122`; the caller is `load_identity(...)` at `src/knok/cli.py:73-75`.

`Identity.save()` creates a new key file with mode `0600`, but `Identity.load()` simply reads the path and parses the PEM. It does not inspect the file's mode, owner, or whether the path is a symlink. Consequently, a key copied from a backup, manually installed, restored with incorrect permissions, or made permissive later is silently accepted (`Identity.save` sets the mode in `os.open(..., 0o600)` at `src/knok/identity.py:93`; `Identity.load` is `src/knok/identity.py:106-122`, whose only filesystem access is `Path(path).read_bytes()` at line 114).

Example: change `identity.key` to mode `0644`. Knok continues to load and use the key even though every local user can read it. The mode set by `save()` protects the initial write; it does not protect the actual runtime trust boundary after the file is changed or provisioned by another mechanism (`src/knok/identity.py:93`, the `os.open` mode argument).

The spec says the private key is held in a file with mode `0600`, owned by the agent's user (§3). Enforce that invariant when loading, or make the policy explicit if non-POSIX platforms are supported. At minimum, reject group/world-readable files on POSIX and report a clear error. Consider checking ownership as well where the process has a meaningful per-agent UID. A symlink policy should be deliberate rather than accidental (`docs/SPEC.md:67-68`, under §3 "Actors and trust" at line 65: "mode 0600, owned by the agent's user").

### F2 — Key-file creation is not crash-atomic or durable

**Severity: Low (availability / provisioning reliability, not key disclosure)**  
**Location:** `src/knok/identity.py:94-103`. *Verified at 828c9791:* `Identity.save` spans `src/knok/identity.py:86-96`; the exclusive create is `os.open(target, os.O_WRONLY \| os.O_CREAT \| os.O_EXCL, 0o600)` at line 93 and the write is `handle.write(pem)` at line 95.

The key is written directly to its final path after an exclusive create. If the process or machine stops during `handle.write(pem)`, a truncated file remains at the final name. The next key-generation attempt refuses to overwrite it, while `load()` fails to parse it. Recovery requires an operator to identify and remove the incomplete file before generating or restoring the key (`src/knok/identity.py:93-95`, direct write to the final path; `handle.write(pem)` at line 95; existing-file refusal at lines 89-90; unguarded parse at line 114).

The use of `O_EXCL` correctly prevents overwriting an existing key and avoids a simple check-then-create race. The weakness is only interruption handling: there is no temporary file, atomic rename, flush/fsync, or directory fsync. Write to a same-directory temporary file with restrictive permissions, fsync it, atomically install it without replacing an existing destination, then fsync the directory. If this is intentionally a minimal provisioning utility, document that a failed generation may leave a partial file and provide a safe recovery instruction (`src/knok/identity.py:86-96`: no temporary path, no `os.replace`, and no `flush`, `fsync` or directory `fsync`).

## Approval and trust binding

The contact approval implementation is materially stronger than a name-only approval:

- `Contacts.pending()` returns the peer, request text, presentation time, and fingerprint that arrived with the request. The request record is local; the peer sees `requested`, not the internal `held` state (`src/knok/contacts.py:239-247`, `pending`; `wire_state` maps `held` to `requested` at lines 224-231, line 231).
- `approve()` requires the fingerprint supplied by the caller to equal the fingerprint stored with the presented request. A mismatch is refused. The decision row records both presented and decided fingerprints; on the approval path they are equal by construction (`src/knok/contacts.py:349-376`, `approve`; mismatch refusal at lines 369-370; both fingerprints recorded at line 375).
- `deny()` deliberately records a mismatch instead of refusing it. Refusing a rotated key is safe, and the audit should preserve which key was presented and which key was on screen when the owner denied it (`src/knok/contacts.py:379-405`, `deny`; `_record_decision(peer, row[0], fingerprint or row[0], "denied", ...)` at line 404).
- Decisions are append-only. A later presentation/decision supersedes the earlier row instead of silently rewriting its history (`src/knok/contacts.py:137-161`, `_record_decision`, which only `INSERT`s into `decisions` at lines 159-161 and never updates or deletes a row).
- `accept()` separately requires an approved decision. A contact request cannot become accepted merely because a caller invokes `accept()` (`src/knok/contacts.py:408-421`, `accept`; `row[0] != "approved"` refusal at lines 417-418).

This matches SPEC §9 and the decision described in the code. The owner-facing presentation itself cannot be verified in this review: the inspected CLI exposes send/recv/inbox/notices/retry commands, but no contact-approval UI or command. The Contacts API supplies the data needed for a prompt; it does not prove what a separate caller actually displayed (`docs/SPEC.md:529-538` and `docs/SPEC.md:547-549`; the CLI subcommands at `src/knok/cli.py:885-946` are `send`, `recv`, `inbox`, `notices` and `retry`).

One audit caveat: `decided_by` is supplied by the caller to `approve()` and `deny()`; Contacts does not authenticate it against the operating-system user or another identity provider. The stored actor is therefore an assertion made by the caller, not independently verified attribution. That is acceptable if only a trusted owner-controlled process can call this local API. It is not a reliable multi-user audit identity without an authenticated caller boundary (`src/knok/contacts.py:349` and `src/knok/contacts.py:379` take `decided_by` from the caller; it is stored at lines 372-373 and 400-402 without any check).

## Key separation and exposure

- Ed25519 is used for signing. X25519 is a distinct key type used by the HPKE implementation; no Ed25519 private key is reused as an X25519 key (`src/knok/identity.py:18` imports only the Ed25519 primitives; `src/knok/hpke.py:26` imports `X25519PrivateKey`, generated at line 118).
- `hpke.py` generates an ephemeral X25519 key for each seal operation and accepts the recipient's raw X25519 private bytes as an argument when opening. The reviewed scope contains no persistent X25519 private-key generation/storage path. The bridge's sealed-envelope receive path is not yet live, so there is no evidence here of an integrated recipient-key vault. The key-management implications of the HPKE flow belong in Review 05 (`src/knok/hpke.py:103-118`, `seal`, fresh `X25519PrivateKey.generate()` at line 118; `src/knok/hpke.py:128-137`, `open_sealed`, `from_private_bytes(recipient_private)` at line 137; the other generation site, `src/knok/transport.py:101`, keeps only `.public_key().public_bytes(...)`; `unseal` is defined at `src/knok/envelope.py:288` with no caller in `src/`).
- The signing private key is serialised unencrypted as PKCS#8 PEM. Its protection is the OS file permission and host/user boundary, not encryption at rest. A copied key file or host-level compromise gives the attacker the ability to sign as that agent (`src/knok/identity.py:92`, `private_bytes(Encoding.PEM, PrivateFormat.PKCS8, NoEncryption())`).
- The reviewed code prints the private-key file path, public key and fingerprint during key generation, not private-key bytes. Identity error messages can disclose a path and public fingerprint, but no private material. No private key is included in an envelope or Agent Card (`src/knok/keygen.py:31-34` prints agent id, fingerprint, public key and the key path; `src/knok/identity.py:116` and `:120` name a path and a fingerprint, never key bytes).
- Python objects retain the private-key object in process memory for as long as the `Identity` object is reachable. There is no explicit zeroisation; this is normal for this Python/cryptography design and should not be represented as secure memory erasure (`src/knok/identity.py:66-69`, the frozen `Identity` dataclass holding `private_key`).

## Known implementation boundary — rotation and revocation

This is a documented incomplete phase, not a new finding.

`registry.py` has a useful `KeyRecord` model: it checks that a fingerprint matches the public key and can report `valid`, `not-yet-valid`, `expired`, `revoked`, or `superseded` for a given instant. `verify_card()` can consult a `Registry` object (`src/knok/registry.py:60-71`, `fingerprint_matches`; `KeyRecord.status` at `src/knok/registry.py:105-120`; `Registry.add` at lines 202-212; the `Registry` branch of `verify_card` at `src/knok/agentcard.py:117-126`).

The live hub path does not currently use that model. `Hub.__init__` accepts a `dict[str, str]` and copies it with `dict(registry)`; `Hub._card_public_key()` then passes that plain dictionary to `verify_card()`. The dictionary form means every included key is valid forever. There is no per-agent key history at the hub, no key-revocation command, and no registry publication/fetch path. Removing a key from the dictionary withdraws it immediately but also loses historical verification; leaving it in means it remains valid indefinitely (`src/knok/hub.py:497`, `registry: dict[str, str]`; `src/knok/hub.py:515`, `self.registry = dict(registry)`; `src/knok/hub.py:637`, `verify_card(card, self.registry, ...)`; the dict branch is `src/knok/agentcard.py:127-130`; `Registry.from_dict` fills `datetime.min` / `datetime.max` bounds at `src/knok/registry.py:243-250`).

Decision 0002 and SPEC §4 explicitly say signed registry records and publication are not implemented yet. The sender-asserted `sentAt` limitation is also already recorded in issue #90 and SPEC §4; it should not be counted again as a newly discovered key-handling defect (`docs/decisions/0002-registry-and-key-records.md:63-69`, "What is not implemented yet"; `docs/SPEC.md:103-105` and `docs/SPEC.md:121-124`; the `sentAt` limitation at `docs/SPEC.md:113-120`).

## Failure behaviour and test coverage

- Missing key file: `Path.read_bytes()` raises `FileNotFoundError`; malformed/truncated PEM raises the cryptography loader's exception. These are not converted to a stable `IdentityError` by `load()`. In the CLI path, that can surface as a traceback rather than a concise provisioning error (`src/knok/identity.py:114`, unguarded `Path(path).read_bytes()` plus `load_pem_private_key`; `load` at `src/knok/identity.py:106-122` wraps neither in `IdentityError`).
- Wrong key type: explicitly refused with `IdentityError` (`src/knok/identity.py:115-116`).
- Wrong identity/key pairing: refused by fingerprint comparison before the key is returned (`src/knok/identity.py:118-121`).
- Existing destination: `save()` refuses overwrite (`src/knok/identity.py:89-90`).
- Invalid/tampered card: card verification fails closed; a bad file is dropped from `load_cards()` rather than stopping the entire directory load (`src/knok/bridge.py:130-133` skips a card whose body does not verify; `src/knok/agentcard.py:131-161` returns `(False, reason)` instead of raising).
- Card identity binding: the signed `name@hub` is checked; a card cannot be moved to another filename to grant its key authority over that filename's identity (`src/knok/bridge.py:117-121`; `src/knok/cli.py:113-114`).
- Card expiry: `validUntil` is checked on use by the bridge; an unreadable stated expiry is refused (`src/knok/bridge.py:299-305`, `card_valid_until` re-read per call, `CardTimeError` refused at lines 301-304, expiry check at line 305).
- Approval mismatch: approval refuses a key that differs from the fingerprint presented; denial records the mismatch (`src/knok/contacts.py:369-370` and `src/knok/contacts.py:404`).

The specified tests were reviewed statically, not run. Existing tests cover key generation uniqueness, key-file mode on initial save, overwrite refusal, save/load round-trip, fingerprint mismatch, card signature and identity binding, card expiry, and approval/denial fingerprint history. They do not cover permissive key-file loading, wrong file ownership, interrupted key writes, or the hub's inability to consume the record-based registry (`tests/test_identity.py:9-12` uniqueness, `tests/test_identity.py:27-29` and `tests/test_keygen_cli.py:19` mode `0600`, `tests/test_identity.py:30-31` and `tests/test_keygen_cli.py:22-30` overwrite refusal, `tests/test_identity.py:34-37` round-trip, `tests/test_identity.py:40-43` fingerprint mismatch, `tests/test_agentcard.py:28-48` and `tests/test_pinned_identity.py:51` card signature and id binding, `tests/test_card_expiry.py:54` and `:73` expiry, `tests/test_contacts_approval.py:120` and `:130` approval/denial fingerprint history).

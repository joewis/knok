## Outcome table

HTTP response rows assume the client raises `HubRefused` for a non-success HTTP response; the retry code itself only treats `exc.retryable` (the 429 path) specially. The exact network-exception-to-`HubError` mapping is owned by `HubClient`, outside this brief. The retry/CLI layer collapses every caught `HubError` to 3. It retries 429 in-process twice (with 2s and 4s sleeps); a third 429 returns 5. Other `HubRefused` responses return 2 without an in-process retry. (`HubClient._request` wraps `OSError` as `HubError` at `src/knok/hubclient.py:131-132`; `except HubError: return 3, None` at `src/knok/cli.py:235-237`; `if exc.retryable and attempt < 3` with `time.sleep(2 * attempt)` at `src/knok/cli.py:224-225`, `return EXIT_RATE_LIMITED` at line 233, `return 2` at line 234; the 2s/4s waits are `2 * attempt` on attempts 1 and 2).

For notice-driven retries: `refused/limits` is retryable (one hour, then one day); `refused/policy|thread|malformed|blocked|unknown`, `expired`, and `dead` are terminal; `gap` and `late` are not send retries. A due retry is reserved before deposit. Single-message exits are 0 for hub acceptance, 1 deferred/not performed, 2 refusal, 3 unreachable, 4 terminal/unknown, and 5 exhausted 429. Scan mode returns 1 if due work could not be performed, otherwise the worst performed status (3 > 2 > 5 > 0). (`RETRYABLE_RULE = "limits"` at `src/knok/retry.py:167` with `BACKOFF_LIMITS = (timedelta(hours=1), timedelta(days=1))` at `src/knok/retry.py:154`; the refused rules in `decide_notice` at `src/knok/retry.py:445-478`, `expired`/`dead` at `src/knok/retry.py:479-489`, `gap`/`late` at `src/knok/retry.py:434-441`; reservation at `src/knok/cli.py:803-816`; single-message exit codes as implemented at `src/knok/cli.py:857-869` and as documented, including 5, at `src/knok/cli.py:618-624`; scan worst status at `src/knok/cli.py:870-875` with `_PERFORMED_SEVERITY = {0: 0, 5: 1, 2: 2, 3: 3}` at `src/knok/cli.py:581`).

## Findings

### F1 — Concurrent retry commands can both spend the same budget slot

**Severity: Medium**
**Location:** `src/knok/retry.py:289-309` (`retry_count`: the set comprehension `attempts = {record.get("attempt") ...}` at lines 296-302 keeps one element per `attempt` value for `decision in ("retry", "reserved")`, and returns `len(attempts) + (1 if unnumbered else 0)` at line 309); `src/knok/cli.py:626-630` (`cmd_retry` reads the ledger once at scan start, `retries = read_retries(directory)` at line 630); `src/knok/cli.py:799-817` (`cmd_retry` phase two: `reservation = _retry_record(notice, decision, now, reserved=True)` at line 803, `record_retry(directory, reservation)` at line 804, `retries.append(reservation)` at line 816, then `_retry_envelope(state, identity, message_id)` at line 817).

**Evidence:** `retry.py:289-309` counts reservations by the set of attempt numbers. `cli.py:626-630` reads the retry ledger once at scan start. `cli.py:799-817` later appends a reservation and deposits without re-reading or locking the ledger.

**Demonstrating command:** Run two `knok retry --message-id <same-id>` processes concurrently after the same `refused/limits` notice is due.

**Observed code path:** Both processes can read a ledger with zero retries and independently decide attempt 1. Both append a `reserved` record with `attempt: 1`, then both call `_retry_envelope`. The set-based count treats those two reservations as one retry. A later scan can therefore still see only one budget unit spent even though two deposits were performed. The same race can occur on attempt 2 and exceed the two-retry ceiling. (`src/knok/retry.py:296-302`, `retry_count`: two `reserved` records sharing `attempt: 1` are one set element, so `len(attempts)` at line 309 counts one).

The receiver's message-ID dedupe reduces the chance of duplicate application delivery, but it does not make the budget reservation atomic: both processes perform network work, and both can consume the same slot. No lock or compare-and-reserve operation protects `retries.jsonl`. (`src/knok/queue.py:509-512`, `Queue.put` returns `"duplicate"` on a seen `message_id`; `src/knok/retry.py:352-367`, `record_retry` opens the ledger with `open(path, "a", encoding="utf-8")` at line 360 — an append with no lock or compare-and-reserve).

### F2 — A terminal decision for an old notice permanently masks newer notices for that message

**Severity: Medium**
**Location:** `src/knok/retry.py:317-325` (`terminal_record`: matches on `record.get("messageId") == message_id and record.get("decision") == "terminal"` at line 323, with no notice-time comparison); `src/knok/cli.py:632-638` (`cmd_retry` building `latest` per message ID, `latest[message_id] = notice` at line 638); `src/knok/cli.py:719-733` (`decided = terminal_record(retries, message_id)` at line 722, `if decided is not None: ... continue` at lines 723-733); the per-notice model at `src/knok/retry.py:328-349` (`resolved_record`, `record.get("noticeAt") == stamp` at line 346, docstring lines 333-336) and the comment at `src/knok/cli.py:734-736` ("A newer notice is a new failure and is decided fresh below").

**Evidence:** `retry.py:317-325` finds a terminal record using only `messageId`; it does not compare the notice timestamp. `cli.py:632-638` selects the latest notice per message ID, and `cli.py:719-733` checks the message-wide terminal record before checking whether the current notice is new. This conflicts with the stated per-notice resolution model at `retry.py:328-337` and the comment at `cli.py:734-736` that a newer notice is a new failure.

**Demonstrating command:** First run `knok retry --message-id m-1` against a terminal notice (for example, `refused/policy`). Then, after a later event produces a newer `refused/limits` notice for the same `messageId`, run `knok retry --message-id m-1` again.

**Observed output:** The second run reports the old terminal reason and exits 4; it never evaluates the newer limits notice or schedules its retry. (`src/knok/cli.py:723-733` emits the stored `decided.get("reason")` and continues without evaluating the notice; `src/knok/cli.py:865-866` maps a `terminal` decision to exit 4).

A later notice is explicitly supposed to be a new failure, but terminal records are keyed only by message ID. This can suppress a legitimate later retry for the lifetime of the ledger. (`src/knok/retry.py:333-336` states resolution is per notice, not per message, while `src/knok/retry.py:323` keys the terminal record on `messageId` alone).

### F3 — If the post-deposit outcome append fails, a successful retry is not remembered as resolved

**Severity: Medium**
**Location:** `src/knok/cli.py:803-816` (`cmd_retry` writes the reservation before the deposit through `record_retry`, which fsyncs at `src/knok/retry.py:360-363`, then `retries.append(reservation)` at line 816); `src/knok/cli.py:817-833` (`_retry_envelope(...)` at line 817, `delivered=(status == 0)` at line 828); `src/knok/cli.py:834-841` (outcome `_retry_record(notice, decision, now, status=status, delivered=(status == 0))` at lines 837-839, `record_retry` at line 840); `src/knok/retry.py:328-349` (`resolved_record` requires `decision == "retry"` at line 344, `status == 0` at line 345, and a matching `noticeAt` at line 346).

**Evidence:** `cli.py:803-816` fsyncs a reservation before the deposit. `cli.py:817-833` performs the deposit and reports `delivered: true` for status 0. `cli.py:834-841` then attempts to append the outcome record. If that append fails, only the reservation remains. But `retry.py:328-349` recognises resolution only from a `decision == "retry"`, `status == 0` outcome carrying the matching `noticeAt`; a reservation cannot satisfy it.

**Demonstrating command:** Run a due `knok retry --message-id m-1` with the hub accepting the replay, and make the second `record_retry` call (the outcome append, after the reservation) fail.

**Observed output:** The current invocation reports the retry as successful (status 0 / `delivered: true`), but the ledger contains only `decision: "reserved"`. The next scan does not find a resolved record. It treats the same notice as a fresh retry candidate and, if the next backoff is due, deposits the same envelope again as attempt 2. (`src/knok/cli.py:828` reports `delivered=(status == 0)`; the record written at `src/knok/cli.py:564` has `"decision": "reserved"` when `reserved=True`, which `src/knok/retry.py:344-346` cannot match).

The reservation does protect the numeric budget, but it does not preserve the successful outcome. This is precisely the crash/write-failure boundary where the command knows it sent successfully but loses the evidence needed to stop replaying.

### F4 — The `delivered` field means “hub accepted the deposit”, not “recipient received the message”

**Severity: Medium (caller-contract ambiguity)**
**Location:** `src/knok/cli.py:212-238` (`_try_deposit`: `return 0, client.deposit(envelope)` at line 221, which is the whole of what a status 0 means); `src/knok/cli.py:197-208` (`cmd_send` prints `"delivered": status == 0` at line 202 and returns `status` at line 209); `src/knok/cli.py:320-332` (`_retry` prints `"delivered": status == 0` at line 326); `src/knok/cli.py:822-833` and `src/knok/cli.py:837-841` (`cmd_retry` sets `delivered=(status == 0)` at line 828 and line 838); `src/knok/cli.py:429-441` (`cmd_notices` docstring, lines 432-435: "``send`` exits 0 when the hub accepted the envelope; delivery can still fail afterwards").

**Evidence:** `cli.py:212-238` returns status 0 as soon as `client.deposit(envelope)` returns. `cli.py:170-208` prints `"delivered": status == 0` for `send`; `cli.py:325-344` does the same for `send --retry-of`. In the retry command, `cli.py:822-833` and `cli.py:837-840` also set `delivered` from that deposit status. Yet the CLI's own `notices` documentation says a send exits 0 when the hub accepted the envelope and a later gate refusal, expiry, or dead-letter can still occur (`cli.py:390-400`). (`src/knok/cli.py:202`, `src/knok/cli.py:326`, `src/knok/cli.py:828` and `src/knok/cli.py:838` all derive the field from the deposit status alone; the statement quoted here is at `src/knok/cli.py:432-435` in this commit).

**Demonstrating command:** `knok send --to <peer> --text <body>`, where the hub accepts the envelope but the recipient later refuses it or the message expires.

**Observed output:** The immediate JSON line contains `"delivered": true` and the command exits 0. A later `knok notices` can report that the same message was refused or expired. (`src/knok/cli.py:197-209`: the immediate object carries `"delivered": true` and the command returns the deposit `status`; the later failure reaches `src/knok/cli.py:429-479`, which reads the `refused`/`expired`/`dead` records from `notices.jsonl`, written by `src/knok/bridge.py:851-866` `_record_notice`).

The transport operation has succeeded, but end-to-end delivery has not been established. The field therefore overstates what the CLI knows. A caller that treats `delivered: true` as proof that the peer received the message can stop monitoring or fail to surface a later failure. The output should distinguish hub acceptance from recipient delivery (for example, `accepted` versus a later delivery notice).

## Other checks

- **Retry identity:** Correct. `send` stores the signed envelope before its initial deposit (`cli.py:245-259`). `_retry_envelope` reads that envelope and passes it unchanged to `_try_deposit` (`cli.py:285-310`). No new ID, context, sequence, timestamp, or signature is minted. `tests/test_send_retry.py` and the retry-policy integration tests assert the same message ID and context at the recipient. A retry is a verbatim envelope replay. (`cmd_send` calls `_remember_attempt(state, envelope)` at `src/knok/cli.py:190`, before `_try_deposit` at line 192; `_remember_attempt` fsyncs the append at `src/knok/cli.py:250-253`; `_retry_envelope` reads the stored envelope through `_find_attempt` at `src/knok/cli.py:293` and hands it unchanged to `_try_deposit` at line 304; `tests/test_send_retry.py:67-68` asserts `retried["contextId"] == first["contextId"]` and `retried["messageId"] == first["messageId"]`, with the end-to-end case at `tests/test_send_retry.py:119-151` and the hub-side replay at `tests/test_retry_policy.py:411`).
- **Budget reservation order:** Reservation is fsynced before the deposit. If that write fails, the retry is not performed and the command marks the work unperformed. This is the correct fail-closed ordering for a single process; F1 is the concurrent-process gap. (`src/knok/cli.py:803-815`: a failed `record_retry` appends the `"the retry could not be counted ... so it was not deposited"` outcome, sets `unperformed = True` at line 814 and `continue`s; the fsync is at `src/knok/retry.py:360-363`).
- **Notice provenance:** A notice for an ID absent from `sent.jsonl` becomes a terminal decision with `record=False`; it is not added to the retry ledger. A successful retry is resolved only when its outcome record matches the notice timestamp. The stale-notice success path is otherwise correct when timestamps are present; F3 covers loss of that outcome record. (`src/knok/retry.py:394-396` returns `_terminal(..., record=False)` when there is no stored attempt; `src/knok/cli.py:757-760` records only when `decision.record` is true; `src/knok/retry.py:338-348` requires the matching `noticeAt`; covered by `tests/test_retry_policy.py:498-514` and `tests/test_retry_policy.py:472-495`).
- **Exit-code contract:** The documented scan severity ordering is implemented explicitly; a performed failure does not exit 0 in scan mode. Single-message mode returns the performed status directly. A due retry that cannot be started because identity/state loading or reservation writing fails exits 1. Unknown IDs and terminal decisions exit 4. No disagreement was found in the normal paths for codes 0, 1, 2, 3, 4, and 5. (`_PERFORMED_SEVERITY = {0: 0, 5: 1, 2: 2, 3: 3}` at `src/knok/cli.py:581`; the scan's worst performed status at `src/knok/cli.py:870-875`; `performed_status` returned directly in single-message mode at `src/knok/cli.py:842-843` and `850-853`; terminal/waiting at `src/knok/cli.py:865-868`; a due retry that cannot be started because identity loading fails sets `unperformed = True` at `src/knok/cli.py:785-797`, which exits 1 at `src/knok/cli.py:867-868`; `tests/test_retry_policy.py:708-733` covers 1 and 4, `tests/test_retry_policy.py:934` the worst performed status).
- **Clock:** Backoff and TTL comparisons use wall-clock UTC timestamps. A backward clock step delays a retry until wall time catches up; it does not itself double-count a retry. A forward step can make a retry due early or make an envelope appear expired. No monotonic-clock protection exists, which is an operational assumption for this file-backed policy. (`not_before = base + backoff[attempt - 1]` at `src/knok/retry.py:404`; the TTL tests at `src/knok/retry.py:406-411`; `due` compares `(now or datetime.now(timezone.utc)) >= decision.not_before` at `src/knok/retry.py:568`; `now` is `datetime.now(timezone.utc)` at `src/knok/retry.py:432` and `src/knok/retry.py:508` — wall clock, with no monotonic source).
- **Ledger growth:** There is no pruning or compaction path for `retries.jsonl`; each performed retry adds a reservation and an outcome, and terminal decisions add records too. The file grows with the agent's history. The broader `sent.jsonl` growth was already explicitly noted in issue #68; the new retry ledger inherits the same unbounded-retention property. This is a storage/maintenance limitation rather than a loop: the retry budget bounds deposits per message, but not ledger size across messages. (`RETRY_LEDGER = "retries.jsonl"` at `src/knok/retry.py:140`; `record_retry` only ever opens `open(path, "a", encoding="utf-8")` at `src/knok/retry.py:360` and nothing truncates or compacts it; `cmd_retry` writes the reservation at `src/knok/cli.py:804` and the outcome at `src/knok/cli.py:840`).
- **Corrupt/truncated ledger:** JSONL readers skip malformed lines independently, so one torn line does not hide later valid records. An unreadable retry ledger produces a warning and is treated as empty for decisions; the actual reservation append then fails and prevents the deposit. A torn reservation is safe to lose because it is written before the deposit. A torn outcome after a successful deposit is the F3 case. (`src/knok/retry.py:246-253` decodes and skips each line on its own; `src/knok/retry.py:239-243` warns and reads an unopenable ledger as empty; `src/knok/cli.py:804-815` refuses the deposit when the reservation cannot be written; `tests/test_retry_policy.py:290-298` and `tests/test_retry_policy.py:802-830` cover the torn and unreadable cases).
- **`notices` command:** The read-only command filters the five bridge notice kinds, preserves JSON records, reports unreadable lines, and rejects non-positive limits. No issue found in the scoped tests. (`NOTICE_KINDS = ("refused", "expired", "dead", "late", "gap")` at `src/knok/cli.py:374`; the kind filter at `src/knok/cli.py:466`; the unreadable-line count at `src/knok/cli.py:454-472`; the non-positive limit rejection at `src/knok/cli.py:446-448`; `tests/test_notices_cli.py:100`, `tests/test_notices_cli.py:122`, `tests/test_notices_cli.py:134`, `tests/test_notices_cli.py:173`).

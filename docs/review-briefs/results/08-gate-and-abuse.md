## Findings

### F1 — The implemented rate limits do not match the limits specified in §9

**Severity: High for a public deployment; Medium for the current private deployment**

**Location:** `src/knok/policy.py:20-25` (`KNOWN_LIMITS` set literal — the only four accepted limit names); `src/knok/gate.py:184-188` (`Gate._within_limits` `pairs` list: `("messages", "all", ...)` at line 185, `("sender", sender, ...)` at line 186, `("messages", "all-day", ...)` at line 187); `src/knok/gate.py:167-178` (`Gate.__init__` reads `policy.limits.get("contact_requests_per_day")` at line 178 and reads no `Policy.probation` attribute); `src/knok/policy.py:106-108` (`probation` defaulted to `False` at line 106) and `src/knok/policy.py:42` (`Policy.probation: bool = False`); `docs/SPEC.md:573-575` (§9 rate limits) and `docs/SPEC.md:508-512` (probation values).

**Evidence:** `policy.py:KNOWN_LIMITS` accepts only `messages_per_hour`, `per_sender_per_hour`, `messages_per_day`, and `contact_requests_per_day`. (`src/knok/policy.py:20-25`) `gate.py:Gate._within_limits` counts `messages_per_hour` under the single key `("messages", "all")` and `per_sender_per_hour` under `("sender", sender)`. (`src/knok/gate.py:185-186`) `Gate.__init__` does not use `Policy.probation` to alter limits. (`src/knok/gate.py:167-178`) The policy parser defaults `probation` to false, but no gate decision reads it. (`src/knok/policy.py:106-117`; no `Policy.probation` attribute is read anywhere in `src/knok/gate.py:1-234`)

**Demonstrating sequence:** Configure the policy with the documented-looking values `messages_per_hour: 100` and `per_sender_per_hour: 20`. Have one sender send 20 messages to this recipient, then send to a second recipient; repeat across recipients.

**Observed behaviour:** The first recipient enforces a 20-per-sender limit locally, but there is no counter shared across recipients enforcing the §9 limit of 100 messages/hour per sender. (`src/knok/gate.py:186`, the key is the bare sender id inside this recipient's own `rates.db`, opened at `src/knok/bridge.py:236`) The 100 value is instead applied as an aggregate inbound limit for this one recipient. (`src/knok/gate.py:185`, key `("messages", "all")`) There is also no hub-wide 10,000/hour counter in the scoped implementation. (`docs/SPEC.md:573-574`; the store schema is per-state-directory at `src/knok/rates.py:27-36`) The probation flag has no effect: the §9 probation limits (20 contact requests/day and 50 messages/day) are not selected or enforced by `Gate` based on that flag, and the §9 5/hour low-engagement throttle is absent. (`docs/SPEC.md:574-578`; no reply-based throttle in `src/knok/gate.py:180-197`)

**Attacker gain / contract violated:** A sender can spread a spray across recipients without hitting the specified per-sender aggregate limit. Probationary agents are not throttled by the specified probation profile. SPEC §9 specifies 100 messages/hour per sender, 20/hour from one sender to one recipient, 10,000/hour per hub, and stricter probation limits. (`docs/SPEC.md:573-575`, `docs/SPEC.md:508-512`) The current limit names and scopes do not implement that model. The hub-wide and low-engagement controls require hub-side work outside this review's scoped files; they are not present in the reviewed gate/policy/rates path. (`src/knok/rates.py:22-25`, a counter store owned by one bridge)

### F2 — A refusal notice is accepted without proving it describes a message the sender actually sent

**Severity: Medium**

**Location:** `src/knok/bridge.py:776-815` (`Bridge._handle_refusal_notice`; the only input checks are `not isinstance(notice, dict)` and `not isinstance(notice.get("messageId"), str)` at line 785); dispatch ahead of the gate at `src/knok/bridge.py:627-629`; notice fields copied into the record verbatim at `src/knok/bridge.py:796-803` (`"messageId": notice["messageId"]` at line 800, `"rule": notice.get("rule")` at line 802); the per-sender cap at `src/knok/bridge.py:788-795` against `MAX_REFUSAL_NOTICES_PER_HOUR = 100` at `src/knok/bridge.py:57`; the test named in the finding is `test_a_notice_flood_is_bounded` at `tests/test_refusal_notice.py:212-233`, whose notice names `m-x` at `tests/test_refusal_notice.py:225`; the rule set it never consults is listed at `src/knok/gate.py:64`; contract at `docs/SPEC.md:593-595`; `sent.jsonl` is `SENT_LEDGER` at `src/knok/retry.py:136`, appended by `src/knok/cli.py:245-259` and read back at `src/knok/retry.py:264-281`, and the handler consults none of it.

**Evidence:** `bridge.py` is outside the listed source scope, but the notice receiver is exercised by `tests/test_refusal_notice.py`. (`tests/test_refusal_notice.py:50`, `tests/test_refusal_notice.py:212`) In `_handle_refusal_notice`, the code checks only that the metadata value is a dict and `notice["messageId"]` is a string. (`src/knok/bridge.py:785`) It does not check that the ID exists in the receiver's `sent.jsonl`, that the stored envelope was addressed to this peer, or that the notice rule is one of the defined refusal rules. (`src/knok/bridge.py:785-803`; `sent.jsonl` itself at `src/knok/retry.py:136`; the defined rules are enumerated at `src/knok/gate.py:64`) The test `test_a_notice_flood_is_bounded` itself constructs a notice naming the arbitrary ID `m-x`. (`tests/test_refusal_notice.py:225`, inside `tests/test_refusal_notice.py:212-233`)

**Demonstrating sequence:** A pinned peer sends a correctly signed ordinary message with `metadata["knok.notice"] = {"kind":"refused","messageId":"some-other-id","rule":"policy"}`. The receiver diverts it to the notice handler before the ordinary gate. (`src/knok/bridge.py:627-629`)

**Observed behaviour:** The receiver records a refusal notice for `some-other-id`, even if it never sent that message to the peer. (`src/knok/bridge.py:796-810`, the frame is built from the notice's own fields and then recorded) The `rule` is also accepted as arbitrary metadata rather than checked against the known rule set. (`src/knok/bridge.py:802`)

**Attacker gain / contract violated:** A pinned peer can inject false failure records into the owner's `notices.jsonl`, mislead the owner about which messages were refused, and create misleading input for the retry CLI. The per-sender cap limits volume but does not establish provenance. (`src/knok/bridge.py:788-795`) SPEC §9 says a notice may describe only the sender's own message; the receiver should correlate the notice's message ID with a locally recorded attempt addressed to that sender, and validate the notice kind/rule before recording it. (`docs/SPEC.md:593-595`; `src/knok/retry.py:420-430`, `decide_notice` consumes a `notices.jsonl` record plus the stored `sent.jsonl` attempt)

### F3 — Approval is keyed to the peer ID, not the key that is current when approval is granted

**Severity: High if a peer can rotate its key while a request is held**

**Location:** `src/knok/contacts.py:239-247` (`Contacts.pending`, returning `a.fingerprint` from the `approvals` row at line 247); `src/knok/contacts.py:349-376` (`Contacts.approve`: the equality test `if fingerprint != row[0]` at lines 369-370, then `self._record_decision(peer, row[0], row[0], "approved", ...)` at line 375, which records the presented value as the decided value); the signature at `src/knok/contacts.py:349-350` accepts no current-registry fingerprint; `src/knok/contacts.py:408-421` (`Contacts.accept`: approval lookup at lines 414-418, state write `self._set(peer, "accepted", ...)` at line 421, keyed on peer id alone); `src/knok/gate.py:220-223` (`Gate.decide` tests `self.contacts.state(sender, moment) != "accepted"` at line 221); contract at `docs/SPEC.md:538-539` and `docs/SPEC.md:557-564`.

**Evidence:** `contacts.py:pending` returns the fingerprint stored when the request arrived. (`src/knok/contacts.py:247`, `a.fingerprint` from the `approvals` join at `src/knok/contacts.py:243`) `Contacts.approve` checks that the caller-supplied fingerprint equals that stored fingerprint, then records the same value as both `presented_fingerprint` and `decided_fingerprint`. (`src/knok/contacts.py:369-375`) It has no current-registry fingerprint input or lookup. (`src/knok/contacts.py:349-350`; `src/knok/contacts.py:1-17`, no registry dependency) `Contacts.accept` then changes the contact state to `accepted` based on the peer ID and approval row alone. (`src/knok/contacts.py:414-421`) `Gate.decide` admits an accepted peer by sender ID; it does not bind that accepted state to the approved fingerprint. (`src/knok/gate.py:220-223`)

**Demonstrating sequence:** Peer P sends a contact request under key K1. While the request remains held, P rotates to K2 and the local registry is updated. The owner approves the pending request using the fingerprint returned by `pending()` (K1), then the contact is accepted. P sends a message signed by K2.

**Observed behaviour:** The approval audit says K1 was presented and approved, but the accepted contact state is attached to P's agent ID. (`src/knok/contacts.py:375`, `src/knok/contacts.py:414-421`) The gate therefore admits the message signed by K2 once the bridge's registry trusts K2. (`src/knok/gate.py:220-223`)

**Attacker gain / contract violated:** A peer can obtain accepted-contact status for a replacement key that was not the key the owner approved. The code's fingerprint equality check only compares the caller's value with the original request record; it does not establish that this is still the key currently attached to the peer. (`src/knok/contacts.py:369-370`) SPEC §9 says approval must be for the key on screen when the owner decides, and that rotation while held must be visible and require refusal plus a fresh request. (`docs/SPEC.md:538-539`, `docs/SPEC.md:557-564`) The approval operation needs the current pinned fingerprint as an independently supplied value and must refuse if it differs from the presented fingerprint; acceptance should remain bound to that approved fingerprint, not just the peer ID.

### F4 — Contact-request state is committed before the owner-presentation record

**Severity: Medium (durability / recoverability)**

**Location:** `src/knok/contacts.py:288-338` (`Contacts.request`: `self._set(peer, LOCAL_HELD, moment, bump=True)` at line 323, the `approvals` insert at lines 324-331, the `contact_requests` insert at lines 332-334, and the commit covering only those two at line 335); `_set` committing its own transaction at `src/knok/contacts.py:269-285` (`self._conn.commit()` at line 285); `pending`'s inner join at `src/knok/contacts.py:241-246` (`JOIN approvals a ON a.peer = c.peer` at line 243); duplicate rejection at `src/knok/contacts.py:301-303`; the seven-day expiry at `src/knok/contacts.py:19` and `src/knok/contacts.py:255-257`.

**Evidence:** `Contacts.request` calls `_set(peer, LOCAL_HELD, ...)` at `contacts.py` before inserting the `approvals` presentation row and `contact_requests` history row. (`src/knok/contacts.py:323-334`) `_set` commits its own transaction. (`src/knok/contacts.py:285`) The presentation and request-history inserts are committed only afterwards. (`src/knok/contacts.py:335`) `pending()` uses an inner join between `contacts` and `approvals`. (`src/knok/contacts.py:243`)

**Demonstrating sequence:** A contact request reaches `Contacts.request`. The process or database fails after `_set` commits but before the approval row is inserted.

**Observed behaviour:** The contact remains `held` (wire state `requested`), but `pending()` cannot display it because there is no matching `approvals` row. (`src/knok/contacts.py:243-244`; the wire view at `src/knok/contacts.py:231`) A repeated request is rejected as a duplicate while the held request remains live. (`src/knok/contacts.py:301-303`, reached because `state` maps `held` to `requested` at `src/knok/contacts.py:231`) The owner has no pending item to approve or deny, and the peer cannot retry until the seven-day expiry. (`src/knok/contacts.py:19`; `approve` requires `local_state(...) == LOCAL_HELD` at `src/knok/contacts.py:365`)

**Attacker gain / contract violated:** A failure at this boundary can strand a contact request in an owner-invisible state. The owner cannot make the decision §9 requires, while the peer is prevented from submitting a replacement request. The contact row, presentation row and request-history row should be one transaction.

### F5 — Message rate limits are fixed calendar buckets, not rolling windows

**Severity: Low to Medium; §9 leaves the window semantics unspecified**

**Location:** `src/knok/rates.py:16-19` (`_bucket`: `%Y-%m-%dT%H` at line 18, `%Y-%m-%d` at line 19); the class docstring that states the doubling at `src/knok/rates.py:22-25` ("a fixed bucket can admit up to twice the limit across a boundary", lines 23-25); durability at `src/knok/rates.py:31-36` and the per-write commit at `src/knok/rates.py:62`; the window spans chosen at `src/knok/gate.py:185-187`; the spec wording it rests on at `docs/SPEC.md:573-574`.

**Evidence:** `rates.py:_bucket` uses `%Y-%m-%dT%H` for hourly counters and `%Y-%m-%d` for daily counters. (`src/knok/rates.py:17-19`) Its docstring explicitly notes that a fixed bucket can admit nearly twice the configured limit across a boundary. (`src/knok/rates.py:23-25`)

**Demonstrating sequence:** Send up to the configured limit immediately before an hour boundary, then send up to the limit again immediately after it.

**Observed behaviour:** Both batches are admitted, so almost twice the nominal hourly allowance can pass within seconds. (`src/knok/rates.py:18-19`) Restart and policy reload do not reset the counters because they are stored in SQLite; moving the wall clock into a new bucket does reset the applicable count. A backward clock step can return to an earlier bucket and its prior count. (`src/knok/rates.py:31-36`, the `rates` table is durable; `src/knok/rates.py:62`, every `hit` commits; `src/knok/bridge.py:378-379`, a reload reuses the same `Rates`; `src/knok/rates.py:18-19`, the bucket is derived from the caller's `moment`, so it follows the wall clock in either direction)

**Attacker gain / contract violated:** A sender can time a burst around bucket boundaries. SPEC §9 says “per hour” but does not define fixed versus rolling windows, so this is a policy/spec ambiguity rather than a clear code violation. (`docs/SPEC.md:573-574`) If the intent is a hard rolling-hour ceiling, use a rolling window or explicitly document the fixed-bucket burst allowance.

## Trust derivation and contact state

There is no numeric `min(person_trust, harness_trust)` calculation in the reviewed implementation. (`src/knok/gate.py:199-234`, the admission path is boolean) Admission is a boolean decision:

1. A local `block` entry always refuses, even if the peer is allow-listed or accepted. (`src/knok/gate.py:218-219`)
2. A local `allow` entry admits without a contact handshake. (`src/knok/gate.py:220`, the negated membership test)
3. Otherwise, a contact in `accepted` state admits. (`src/knok/gate.py:221`)
4. Otherwise, `contact_policy: direct` admits (policy validation permits this only for private/local deployment). (`src/knok/gate.py:222`; the validation at `src/knok/policy.py:91-94`)
5. Everything else is refused before limits and thread checks. (`src/knok/gate.py:223`, ahead of `src/knok/gate.py:231` and `src/knok/gate.py:234`)

The only inputs that raise an unlisted peer to accepted status are the local owner approval followed by `Contacts.accept`. (`src/knok/contacts.py:349-376`, `src/knok/contacts.py:408-421`) No message field or wire state can call either operation. (`src/knok/contacts.py:365`, approve needs `LOCAL_HELD`; `src/knok/contacts.py:417`, accept needs an `approved` row; neither is reachable from `src/knok/gate.py:199-234`) A policy edit can add a peer to `allow`, or switch a private/local policy to direct delivery; those are local configuration actions. (`src/knok/policy.py:110-118`; `src/knok/gate.py:220-222`) A peer's own request only creates local `held` state, exposed on the wire as `requested`. (`src/knok/contacts.py:323`, `src/knok/contacts.py:338`; the wire mapping at `src/knok/contacts.py:231`)

State transitions: `requested/held` expires after seven days; `expired` may request again. (`src/knok/contacts.py:19`, `src/knok/contacts.py:255-257`) `refused` is terminal. (`src/knok/contacts.py:306-307`) `accepted` persists until local `revoke`, which deletes the contact row and returns the peer to `none`. (`src/knok/contacts.py:431-437`; absence maps to `none` at `src/knok/contacts.py:253`) A policy block overrides allow and accepted status. (`src/knok/gate.py:218-219`) A policy reload rebuilds the gate around the same contact/rate/thread stores, so it does not itself erase accepted contacts or counters. (`src/knok/bridge.py:378-379`, with the retained stores created at `src/knok/bridge.py:236-240`)

## Limits and concurrency notes

- Message counters persist across process restart and policy reload because they live in `rates.db`. (`src/knok/bridge.py:236`; the table at `src/knok/rates.py:31-36`) The bridge's shared `Rates` object serializes each individual `count` and `hit`, but `Gate._within_limits` performs all checks and then all increments as separate operations. There is no transaction spanning check-and-hit. (`src/knok/rates.py:48`, `src/knok/rates.py:56`, one in-process lock per call; `src/knok/gate.py:189-196`, every check runs before any increment) Concurrent calls to `decide` can both observe a remaining slot and both consume it. (`src/knok/gate.py:192-196`)
- The message counters are charged only after basic gate validation and only if all configured windows pass. (`src/knok/gate.py:225-232`) A refusal does not consume message quota. (`src/knok/gate.py:231-232`, which returns before any `hit` call) The thread receipt is not applied until the queue insert transaction, which correctly prevents a failed insert or duplicate offer from spending reply credit. (`src/knok/bridge.py:660`; `Receipt.apply` at `src/knok/gate.py:46-51`)
- Contact requests use a rolling 30-day per-peer request history and a three-request cap. (`src/knok/contacts.py:20-21`, `src/knok/contacts.py:261-266`, `src/knok/contacts.py:309-310`) The owner-presentation cap is five distinct pending/presented peer rows in the rolling 24-hour query. (`src/knok/contacts.py:33`, `src/knok/contacts.py:341-346`) The global daily request limit is optional policy configuration, not a built-in default. (`src/knok/contacts.py:314`, fed from `src/knok/gate.py:178`) The request history and `Rates` daily counter are separate commits, so a crash between them can leave the contact request recorded without charging the daily rate counter. (`src/knok/contacts.py:335` then `src/knok/contacts.py:336-337`)
- A second process using the same bridge queue should be excluded by the queue's process lock, but the rate store itself has no cross-process reservation transaction. (`src/knok/rates.py:55-62`, an insert-then-commit under one in-process lock) The scoped rate implementation should not be treated as a hub-wide limiter.

## Blocked-sender cost and silence

The gate refuses blocked and unapproved messages only after the bridge has a verified envelope to evaluate. (`src/knok/bridge.py:608-615`, verification before `src/knok/bridge.py:649`) The gate itself cannot prevent that envelope from first occupying the hub mailbox or causing the recipient bridge to poll and inspect it. (`src/knok/hub.py:341-356`, `_deposit` stores before any recipient gate; `src/knok/bridge.py:649`) That is different from the §9 public-hub requirement that recipient blocklists be published to the hub and blocked delivery refused before the message reaches the recipient bridge. (`docs/SPEC.md:580-583`) Hub-side blocklist publication/enforcement is outside this review's source scope, so this report does not claim it is absent from every hub component; it is not implemented by the reviewed gate/policy/contact code. (`src/knok/gate.py:199-234`, the block test is recipient-side only)

Within the gate, blocked messages do not enter the local application queue or spend thread receipts/rate quota. (`src/knok/gate.py:218-219`, which returns before `_within_limits` at line 231 and before `Threads.receipt` at line 234; `src/knok/bridge.py:650-655`) They are written to the recipient's local refusal log and produce no sender notice. (`src/knok/bridge.py:708-724`) Unapproved but pinned messages are refused with a `policy` notice; unknown/unverifiable senders do not receive a gate notice. (`src/knok/bridge.py:610-611`; `src/knok/bridge.py:723-725`) Malformed or unverifiable items that fail before the gate follow the separate unhandled/drop path (`src/knok/bridge.py:612-623`) and may leave no sender-visible refusal.

## Policy reload

The bridge reloads policy at the start of each poll. (`src/knok/bridge.py:486`) It parses a changed file into a new immutable `Policy`, verifies the `agent_id`, and swaps the policy and gate together. (`src/knok/bridge.py:361-379`; the frozen dataclass at `src/knok/policy.py:34-42`) Invalid, unreadable or wrong-agent files leave the old policy active; a changed file is logged once rather than re-parsed every poll. (`src/knok/bridge.py:347-355`, `src/knok/bridge.py:356-360`, `src/knok/bridge.py:363-372`) Existing `Contacts`, `Threads` and `Rates` objects are retained.

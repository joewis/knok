## Findings

### F1 — Dropped-item ledger retains the complete rejected envelope indefinitely

**Severity: Medium (privacy/data-retention); higher where an agent state directory is shared with less-trusted processes.**

**Location:** `src/knok/bridge.py:831–849` (`_record_drop`), called from `bridge.py:510–520`. Pinned-commit detail: `_record_drop` is defined at `src/knok/bridge.py:831` (`def _record_drop(self, item: Any, key: str) -> bool:`); it sets `path = self.state.directory / "dropped.jsonl"` at `src/knok/bridge.py:838`, builds `record = {"key": key, "at": …, "item": item}` at `src/knok/bridge.py:839`-`840`, and appends it with `open(path, "a", encoding="utf-8")` + `json.dumps(record, sort_keys=True, default=str)` + `flush` + `os.fsync` at `src/knok/bridge.py:842`-`845`. The call is `if not self._record_drop(item, key):` at `src/knok/bridge.py:513`, reached only after `attempts < MAX_HANDLE_ATTEMPTS` fails (`MAX_HANDLE_ATTEMPTS = 5`, `src/knok/bridge.py:53`; test at `src/knok/bridge.py:506`).

When an item exhausts its five handling attempts, `_record_drop` writes:

- a local timestamp and key (`"key"` is the item key from `item_key(item)` at `src/knok/bridge.py:503`; `"at"` is `datetime.now(timezone.utc).strftime("%Y-%m-%dT%H:%M:%SZ")`, `src/knok/bridge.py:839`); and
- `"item": item`, the complete fetched object. (`src/knok/bridge.py:840`; the value is the whole `item` argument of `_record_drop`, `src/knok/bridge.py:831`, serialised with `default=str`)

That object can contain a form-1 message body, message metadata, sender/recipient identifiers, timestamps and the sender's signature. This is not merely envelope metadata. It is written for items the bridge could not successfully handle, including items for which no trusted sender card was found or whose envelope could not be verified. (Those are the `unhandled` branches of `Bridge._handle`: no card `src/knok/bridge.py:609`-`611`, failed `verify_envelope` `src/knok/bridge.py:612`-`615`, no form-1 `message` `src/knok/bridge.py:617`-`623`; all three return `"unhandled", None`, which is what spends the attempt allowance at `src/knok/bridge.py:502`-`505`.) A peer can therefore cause content it sent to be retained in the recipient's local state even though the bridge never accepted it into the application queue.

The file is append-only and has no expiry or pruning path. (`open(path, "a")` at `src/knok/bridge.py:842` is its only access in `src/`; the test asserts the file exists after a drop, `tests/test_delivery_ledger.py:159`.) This differs from the 30-day metadata retention rule for hub logs and the 30-day dead-letter retention specified in SPEC §6; `dropped.jsonl` is not given a corresponding retention policy. (`docs/SPEC.md:634` — "**Logs:** envelope metadata 30 days; bodies zero days on the public hub"; `docs/SPEC.md:356` — "Dead letters are retained 30 days".) It also differs from the public-hub rule that bodies have zero-day log retention: this is a bridge-local record, not a hub log, but the distinction should be explicit.

**Consequence:** an operator (or any process able to read the agent's state) can reconstruct the body of a message the bridge eventually dropped. A peer cannot read this file over the protocol, but a same-UID co-located process can read it if it can access the directory. (`0700` on the state directory is applied at `src/knok/bridge.py:222`; the documented stronger boundary is one container and volume per agent, `docs/HUB.md:183`-`184`.) The file is incidental to the protocol's delivery contract: the spec requires a visible dead-letter record, but does not require this local unhandleable-item ledger to retain the full envelope forever.

**Recommendation:** store only the minimum diagnostic metadata by default; if retaining the full item is operationally necessary, make that an explicit owner-controlled option, encrypt it at rest, and enforce a bounded retention period with documented deletion behavior.

### F2 — Local state permissions do not isolate agents sharing one OS identity

**Severity: Medium when multiple agents share a UID; Low in the documented one-container/one-volume-per-agent deployment.**

**Location:** `src/knok/bridge.py:245–247`; JSONL writers at `bridge.py:573–588, 817–829, 831–849, 851–866, 901–907`; `src/knok/cli.py:244–261`; `src/knok/retry.py:250–263` (ledger writers). Pinned-commit detail: the `chmod` is `src/knok/bridge.py:221`-`222`; the JSONL writers are `_record_deliveries` `src/knok/bridge.py:573`-`592` (append at `src/knok/bridge.py:584`), `_append_line` `src/knok/bridge.py:817`-`829` (at `src/knok/bridge.py:821`), `_record_drop` `src/knok/bridge.py:831`-`849` (at `src/knok/bridge.py:842`), `_record_notice` `src/knok/bridge.py:851`-`866` (at `src/knok/bridge.py:859`), `_append_inbox` `src/knok/bridge.py:901`-`906` (at `src/knok/bridge.py:903`), `_remember_attempt` `src/knok/cli.py:245`-`259` (at `src/knok/cli.py:250`) and `record_retry` `src/knok/retry.py:352`-`367` (at `src/knok/retry.py:360`). None of the seven passes a `mode` argument to `open`.

The bridge sets the state directory to `0700`, but does not set an explicit mode on the JSONL files. (`os.chmod(state.directory, 0o700)` at `src/knok/bridge.py:222`; no `os.chmod` or `os.fchmod` follows any of the seven `open(..., "a")` calls listed above.) Python's append-create mode is filtered through the process umask; SQLite similarly creates its database files under the process identity. (`sqlite3.connect` with no mode argument: `src/knok/queue.py:205`, `src/knok/rates.py:31`, `src/knok/contacts.py:81`, `src/knok/hub.py:539`.) The code does not validate that the state directory is owned by the expected UID, and Unix directory permissions do not separate two processes running as that same UID. (No `st_uid` / `os.getuid` comparison on `state.directory` exists in `src/knok/bridge.py`.)

The files include private or sensitive material: `identity.key`, outbound signed message bodies in `sent.jsonl`, inbound bodies in `inbox.jsonl` and `queue.db`, and the dropped full envelopes identified in F1. (`identity.key` opened with mode `0o600` at `src/knok/identity.py:93`; `"envelope"` written whole at `src/knok/cli.py:247`; `json.dumps(envelope, …)` at `src/knok/bridge.py:904`; `envelope_json` column at `src/knok/queue.py:102`; `"item": item` at `src/knok/bridge.py:840`.) A same-UID sibling agent can read those files if it knows or discovers the paths. The documented topology in HUB.md uses a separate container and volume for each agent; that deployment boundary is doing the isolation work, not per-file access control in Knok. (`docs/HUB.md:171`-`172` and `docs/HUB.md:183`-`184` describe one container, one volume and a `0600` key per agent.)

**Consequence:** a deployment that runs several agents as one Unix user and relies on `0700` directories for isolation does not achieve that isolation. In particular, one agent can read another agent's signing key and stored conversation material. (`identity.key` is read back through `identity_mod.load(...)` at `src/knok/bridge.py:229`-`233`; the key file's `0600` is set by `src/knok/identity.py:93`, which is per-file, not per-UID.)

**Recommendation:** keep the documented per-agent OS/container/volume boundary. If same-host multi-agent isolation is intended without containers, use distinct UIDs and verify directory ownership/mode at startup; explicitly chmod sensitive files and database files rather than relying only on umask.

### F3 — Peer-controlled notice fields can forge terminal and log lines

**Severity: Low to Medium (operator-log integrity / misleading CLI output).**

**Location:** `src/knok/bridge.py:776–815`, especially `804–808`; `src/knok/cli.py:388–425` (`_notice_line`); `src/knok/cli.py:478`. Pinned-commit detail: `_handle_refusal_notice` is defined at `src/knok/bridge.py:776`; the only validation is `if not isinstance(notice, dict) or not isinstance(notice.get("messageId"), str):` at `src/knok/bridge.py:785`; `messageId`, `contextId` and `rule` are copied into the record at `src/knok/bridge.py:800`-`802` and logged with `%s` at `src/knok/bridge.py:804`-`809`; `_notice_line` is `src/knok/cli.py:407`-`426` (values interpolated at `src/knok/cli.py:413`-`425`) and is printed at `src/knok/cli.py:478`.

A pinned peer can send a signed envelope with the `knok.notice` metadata key. The handler checks that `notice` is a dict and that `notice.messageId` is a string, but does not constrain its length or reject control characters; `contextId` and `rule` are also copied without type/format validation. (`src/knok/bridge.py:785`; the copies at `src/knok/bridge.py:801`-`802` are bare `notice.get("contextId")` and `notice.get("rule")`, with no type check, length bound or `isprintable`-style test in `_handle_refusal_notice` `src/knok/bridge.py:776`-`815`.) The JSONL writer escapes newlines correctly, so the stored JSON remains one physical line. (`json.dumps(frame, sort_keys=True)` at `src/knok/bridge.py:860` escapes an embedded newline inside a string.) The human-readable reader then interpolates these values directly into a terminal line, and the bridge logs them with ordinary `%s` formatting. (`src/knok/cli.py:416`-`425`; `src/knok/bridge.py:804`-`809`.) A newline in a peer-supplied message ID or rule can therefore make one notice appear as multiple terminal/log lines, including text that resembles a second event.

The same class of issue exists in other bridge log messages that interpolate peer-supplied `messageId` values (for example, the gate-refusal and duplicate messages at bridge.py:646–654). Call sites: `log.info("re-offered message %s is already queued; acking without gate work", message_id)` at `src/knok/bridge.py:646`; `log.info("gate refused %s from %s: %s", message_id, sender, decision.reason)` at `src/knok/bridge.py:653`. The envelope validator requires a non-empty string for message IDs but does not impose a printable-character restriction. (Form 2: `src/knok/envelope.py:143`-`145`; form 1: the receiver's own re-check at `src/knok/bridge.py:635`; neither adds a character-class test.)

**Consequence:** a pinned peer can make the operator's terminal or centrally collected logs misleading. This does not let the peer write arbitrary bytes to the JSONL file—the JSON encoder escapes them—and it does not expose a body through the notice reader.

**Recommendation:** validate protocol identifiers against a narrow printable syntax at the envelope/notice boundary, and escape control characters in every human-facing log/terminal formatter. Keep JSON output as JSON rather than interpolating untrusted values.

### F4 — The refusal-notice path is an ordinary signed message that bypasses the recipient gate

(`MAX_REFUSAL_NOTICES_PER_HOUR = 100`, `src/knok/bridge.py:57`; check at `src/knok/bridge.py:788`-`795`; hit at `src/knok/bridge.py:814`; the code comment at `src/knok/bridge.py:792`-`793` says a notice is handled before the gate, "so §9's message counters never see it".)

The notice's free-text `parts` are ignored; only selected metadata fields are copied to the local notice record. (`parts` are built sender-side at `src/knok/bridge.py:756`-`758` and never read in `_handle_refusal_notice` `src/knok/bridge.py:776`-`815`; `docs/SPEC.md:401` — "diverts a notice to `notices.jsonl` before the gate and never delivers it to an agent" — states the intent.) Thus this is not a way to deliver arbitrary body text to the agent application or to bypass the gate with a hidden payload. It is a way to bypass the gate's *message accounting* and pollute the owner's operational record with false notice metadata. (`docs/SPEC.md:402`-`403` fixes `rule` to the gate's own categories — `policy`, `limits`, `thread`, `malformed` — and `src/knok/bridge.py:802` copies a peer-supplied value into the file.)

**Consequence:** a pinned peer can claim that it refused a message the local agent never sent, invent the rule and message ID shown in `knok notices`, and consume the separate notice allowance. It cannot use the path to make the application receive the ignored body.

**Recommendation:** correlate each incoming notice with a locally recorded outbound attempt addressed to that sender; validate `rule` against the defined set and validate the context/message relationship before recording it. Consider counting notices against an independent but explicit hub/recipient quota.

### F5 — Local audit files and retry ledgers have no retention policy

**Severity: Medium (privacy and storage growth).**

**Location:** `bridge.py:550–588` (`delivery.jsonl`), `bridge.py:710–725` (`refused.jsonl`), `bridge.py:831–866` (`dropped.jsonl` / `notices.jsonl`); `cli.py:244–261` (`sent.jsonl`); `retry.py:250–263` (`retries.jsonl`). Every writer opens with mode `"a"`; none truncates, rotates or deletes.

All of these files are append-only. No code in the reviewed paths rotates, truncates, compacts or prunes them. `sent.jsonl` and `dropped.jsonl` contain complete envelopes/items, while `delivery.jsonl`, `refused.jsonl`, `notices.jsonl` and `retries.jsonl` retain identifiers, peer relationships, rules, outcomes and timestamps. (`{"recordedAt": …, "envelope": envelope}` `src/knok/cli.py:247`; `"item": item` `src/knok/bridge.py:840`; `"messageId"`, `"outcome"`, `"kind"`, `"from"`, `"to"`, `"seq"`, `"contextId"` `src/knok/bridge.py:559`-`570`; `"at"`, `"rule"` `src/knok/bridge.py:711`-`715`; `"kind"`, `"from"`, `"receivedAt"`, `"rule"` `src/knok/bridge.py:796`-`803`; `retries.jsonl` decisions `src/knok/cli.py:547`-`590`.) The retry adapter needs the original envelope to replay it, but only until its expiry/retry window; it does not need every historical attempt forever. (`read_attempts` keeps only the last stored envelope per `messageId`, `src/knok/retry.py:264`-`275`; the replay budget is `MAX_RETRIES = 2`, `src/knok/retry.py:130`.)

The hub's 72-hour mailbox TTL and 30-day dead-letter retention do not prune these bridge-local copies. (`FRAME_TTL = timedelta(hours=72)` `src/knok/hub.py:104`; frames `docs/HUB.md:107`-`109`; default TTL 72 h / maximum 30 days `docs/SPEC.md:376`; dead letters 30 days `docs/SPEC.md:356`.) Deleting an inbox/ledger file would also not securely erase historical SQLite pages or backups where those exist. (Nightly encrypted backup of queue and registry `docs/SPEC.md:623`-`625`; `src/` contains no `VACUUM` and no secure-delete call.)

**Consequence:** local message bodies and metadata accumulate beyond the lifetime of the corresponding hub item. The audit trail can reveal communication partners, context IDs, refusal rules and activity times long after delivery or expiry. Disk use is unbounded.

**Recommendation:** define per-file retention explicitly. Keep retryable sent envelopes only until expiry plus a short operational grace period; retain metadata audit rows for a documented period (30 days would align with the spec's stated log-retention target); prune or rotate with atomic replacement and account for SQLite WAL/backup copies. Make any longer retention an explicit owner choice.

## Direct answers to the brief's questions

1. **Inventory:** see the table above. The application has no in-repo log file handler or rotation policy in the reviewed paths; destination and retention for Python logs are delegated to the embedding runtime. (`src/knok/bridge.py:47` declares the logger; `logging.basicConfig(..., stream=sys.stderr)` at `src/knok/runner.py:137`-`141` is the only handler configuration in `src/`.)
2. **Content:** `inbox.jsonl`, `sent.jsonl`, `queue.db` and `dropped.jsonl` can contain message bodies. (`src/knok/bridge.py:904`, `src/knok/cli.py:247`, `src/knok/queue.py:102`, `src/knok/bridge.py:840`.) `sent.jsonl` needs the original envelope for verbatim retry; `inbox.jsonl` and `queue.db` are the local delivery/application store. The full item in `dropped.jsonl` is incidental and excessive. Local audit/notice files contain metadata, not bodies. The public hub is specified to retain bodies in its queue only while queued, and not in logs; nightly encrypted backups also contain queue data, with backup retention unspecified. (`docs/SPEC.md:634` — bodies "zero days on the public hub"; `docs/SPEC.md:623`-`625` — nightly encrypted backup of queue and registry, with no retention period stated in `docs/SPEC.md` or `docs/HUB.md`.)
3. **Reconstruction:** an operator with access to `dropped.jsonl` can reconstruct an unhandleable message body. A process with access to `inbox.jsonl`, `sent.jsonl` or `queue.db` can reconstruct ordinary stored messages. A blocked peer's attempt is recorded in local `refused.jsonl` with sender, ID, context, rule and time, but no body. (`"at"`, `"messageId"`, `"contextId"`, `"from"`, `"rule"` at `src/knok/bridge.py:711`-`715`.) That record is not sent to the peer. A peer cannot read these local files through the protocol.
4. **Errors:** bridge logs include exception strings for fetch/ack/write/policy/queue/notice failures and a traceback for an unexpected poll exception (`log.exception`, bridge.py:918–919). Log call sites: `log.exception("poll failed; continuing")` at `src/knok/bridge.py:919`, `log.warning("ack failed …")` at `src/knok/bridge.py:544`, `log.error("could not write inbox …")` at `src/knok/bridge.py:895`, `log.warning("could not record notice …")` at `src/knok/bridge.py:865`. They do not explicitly log `repr(envelope)` or a private identity. Some exception strings can reveal local paths or implementation details; no reviewed path formats an exception into a notice. CLI errors print exception strings for hub and filesystem failures. The full item is persisted by F1, not printed as an exception.
5. **Notices:** refusal notices are ordinary signed messages across the hub, with 24-hour envelope expiry; they use hub mailbox capacity and deposit controls. (`expiresAt` `src/knok/bridge.py:764` with a 24-hour expiry, `docs/SPEC.md:392`; mailbox caps `src/knok/hub.py:92`-`93`.) On receipt they are intercepted before the normal gate, are not delivered to the application, do not create a reply, and do not naturally loop. They have a separate 100-per-sender-per-hour local cap. (`MAX_REFUSAL_NOTICES_PER_HOUR = 100`, `src/knok/bridge.py:57`; `src/knok/bridge.py:788`-`795`; `self.rates.hit("notice", …)` `src/knok/bridge.py:814`.) The body parts are ignored; unvalidated metadata can forge notice records but cannot deliver arbitrary body text.
6. **Injection:** JSONL writers use `json.dumps`, which escapes embedded newlines. (`src/knok/bridge.py:822`, `src/knok/bridge.py:843`, `src/knok/bridge.py:860`, `src/knok/bridge.py:904`, `src/knok/cli.py:251`, `src/knok/retry.py:361`.) Human-readable log and terminal formatters do not escape all peer-controlled identifiers/notice fields; F3 covers the resulting line injection. (`src/knok/cli.py:413`-`425`; `src/knok/bridge.py:646`, `src/knok/bridge.py:653`, `src/knok/bridge.py:804`-`809`.)
7. **Owner activity:** no owner keyboard/read/approval timestamp is put in the reviewed notice wire path. (Wire fields: `src/knok/bridge.py:743`-`745`, `763`; the receiver's record: `src/knok/bridge.py:796`-`803`.) Bridge processing timestamps are visible, but they are not owner-attention timestamps.
8. **Retention:** local JSONL audit, notice and retry files have no pruning. (Writers listed under F5, `src/knok/bridge.py:582`-`862`, `src/knok/cli.py:245`-`259`, `src/knok/retry.py:352`-`367`; no truncate/rotate/unlink on those names in `src/`.) Queue rows and hub frames have their protocol TTL/ack behavior; SQLite/WAL and nightly backups are not secure-erasure mechanisms. Backup retention is unspecified.
9. **Reader trust:** the code assumes the state directory is the security boundary. It chmods the bridge directory to `0700`, but does not set explicit JSONL/SQLite file modes or verify directory ownership. (`os.chmod(state.directory, 0o700)` `src/knok/bridge.py:222`; the `open(..., "a")` and `sqlite3.connect` calls listed under F2 take no mode; no `st_uid` check in `src/knok/bridge.py`.) A different UID is blocked by the directory on a normal Unix filesystem; a same-UID sibling process is not. The documented per-agent container/volume boundary must remain in place if agents are mutually untrusted.

## Overall assessment

The peer-facing notice design is narrow: it reports only metadata about a message the peer allegedly sent, and does not deliver notice body text to the application. The important privacy weakness is local retention, not a direct remote read: `dropped.jsonl` stores full unhandleable items indefinitely, while several other body-bearing files also have no pruning. (`src/knok/bridge.py:838`-`845`; the writers and their absence of retention are listed under F5.) The important isolation caveat is that `0700` is per-UID, not per-process. (`src/knok/bridge.py:221`-`222`.) Keep agents on separate OS/container identities, stop retaining full dropped envelopes by default, add retention, and escape untrusted strings in logs and terminal output.
